# RAG 최적화

## 1. 과정 개요

- 과정명: 실무형 RAG 시스템 구축 및 최적화
- 교육 시간: 40시간(5일 × 8시간)
- 대상: 기본 RAG 파이프라인을 구현해 본 학습자
- 적용 사례: 작업표준서, 설비 매뉴얼, 품질 기준서, 정비 이력 검색
- 최종 산출물: 기준선 대비 개선 효과를 수치로 설명하는 RAG 평가 리포트

이 과정의 목표는 기법을 많이 붙이는 것이 아니라 실패 원인을 측정하고 가장 작은 변경으로 검색과 답변 품질을 개선하는 것이다.

```text
측정 → 실패 분류 → 한 가지 변경 → 재평가 → 채택 또는 롤백
```

## 2. 학습 목표

교육 종료 시 학습자는 다음을 수행할 수 있어야 한다.

1. 골든셋으로 RAG 기준 성능을 측정한다.
2. 검색 실패와 생성 실패를 분리해 진단한다.
3. 제조 약어와 동의어를 반영해 질의를 재작성한다.
4. 키워드 검색과 벡터 검색을 결합한다.
5. 리랭킹과 부모 문서 검색으로 문맥 품질을 높인다.
6. 근거성, 정답성, 지연시간, 비용을 함께 평가한다.
7. 문서에 근거가 없을 때 답변을 보류하도록 설계한다.

## 3. 최적화 대상

```text
사용자 질문
  → 질의 이해·재작성
  → 후보 문서 검색
  → 필터링·리랭킹
  → Context 구성
  → 답변 생성
  → 인용·검증
```

| 구간 | 대표 실패 | 주요 개선 방법 |
|---|---|---|
| 문서 수집 | 최신 개정본 누락, 표·제목 손실 | 수집 검증, 구조 보존, 버전 메타데이터 |
| Chunking | 절차와 경고문 분리 | 구조 기반 분할, overlap 조정 |
| 질의 처리 | 약어·설비 코드 인식 실패 | 정규화, 동의어 확장, Multi-Query |
| 검색 | 정확한 부품 번호를 놓침 | 키워드+벡터 하이브리드 검색 |
| 후보 정렬 | 관련성이 낮은 문서가 상위 노출 | 리랭커, 메타데이터 필터 |
| Context | 중복·상충 문서 혼합 | 중복 제거, 최신 문서 우선, 토큰 예산 |
| 생성 | 근거 없는 추론, 인용 불일치 | 근거 제한, 인용 검증, 답변 보류 |

> 검색되지 않은 사실은 생성 단계에서 복구하기 어렵다. 검색된 근거가 부정확하면 자연스러운 답변도 좋은 답변이 아니다.

## 5. D15 — 검색 품질 진단

### 골든셋 설계

골든셋은 질문마다 기대 답변과 정답 근거를 함께 기록한다.

| 필드 | 설명 | 예시 |
|---|---|---|
| `question_id` | 질문 식별자 | `Q-001` |
| `question` | 사용자 질문 | `CNC-02 주축 과열 시 점검 순서는?` |
| `expected_answer` | 기대 답변의 핵심 | `정지→전원 차단→냉각계 점검` |
| `relevant_doc_ids` | 정답 문서 ID | `SOP-CNC-017` |
| `relevant_sections` | 정답 구간 | `4.2 과열 대응` |
| `query_type` | 질문 유형 | 절차, 수치, 비교, 없음 |

정확한 명칭, 약어·오탈자, 다중 문서, 개정본 충돌, 표의 수치, 문서에 답이 없는 질문을 고르게 포함한다.

### 검색 평가 지표

정답 문서 집합을 `R`, 상위 `k`개 검색 결과를 `Sₖ`라고 한다.

```text
Recall@k    = |R ∩ Sₖ| / |R|
Precision@k = |R ∩ Sₖ| / k
Hit@k       = 정답 문서가 하나라도 있으면 1, 없으면 0
MRR         = 첫 번째 정답 문서 순위의 역수 평균
```

검색 평가에서는 답변을 생성하지 않는다. Retriever가 반환한 문서 ID와 골든셋의 정답 문서 ID만 비교한다.

### 기준선 설정

```yaml
experiment_id: baseline-001
chunk_size: 800
chunk_overlap: 120
retriever: vector
top_k: 5
metadata_filter: active_documents_only
```

설정, 문서 버전, 코드 버전, 실행 시각을 함께 보존해야 실험을 재현할 수 있다.

## 6. D16 — 질의 재작성과 Multi-Query

제조 질문에는 설비 코드, 약어, 한·영 혼용이 자주 등장한다. 원문 질문을 보존하면서 검색용 질문만 정규화한다.

```text
원문: 2호기 spindle temp 알람 조치?
정규화: CNC 2호기 주축 온도 경보 발생 시 조치 절차
확장어: spindle=주축, temp=온도, alarm=경보
```

권장 순서는 설비 ID 추출 → 승인된 용어 사전 적용 → 단위 정규화 → 검색 의도를 유지한 짧은 질의 생성이다. LLM만으로 설비 코드를 추측하지 않는다.

Multi-Query는 하나의 질문을 관점이 다른 2~4개의 검색 질의로 변환한다.

```text
질문: 프레스 유압이 떨어질 때 확인할 것은?
질의 1: 프레스 유압 저하 점검 절차
질의 2: hydraulic pressure low 원인과 조치
질의 3: 프레스 압력 부족 트러블슈팅
```

결과는 `doc_id + section_id` 기준으로 중복 제거한다. 부품 번호나 오류 코드가 있는 질문은 원문 키워드 검색도 반드시 유지한다.

## 7. D17 — 하이브리드 검색과 리랭킹

키워드 검색은 오류 코드·규격 번호·부품명에 강하고, 벡터 검색은 의미가 비슷한 표현에 강하다.

```text
키워드 검색 ─┐
             ├→ 순위 결합 → 후보 문서 → 리랭킹 → 최종 Context
벡터 검색 ───┘
```

서로 다른 검색 점수는 단순 덧셈하지 않고 순위 기반 결합부터 실험한다.

```text
RRF(d) = Σ 1 / (c + rankᵢ(d))
```

반드시 고려할 메타데이터:

- 사업장·라인·설비 ID
- 문서 종류와 적용 제품군
- 시행일, 개정 번호, 폐기 여부
- 보안 등급과 사용자 권한
- 언어와 기준일

1차 검색은 넓게 후보를 모으고 리랭커로 직접 관련성을 다시 평가한다. 예를 들어 후보 20~50개를 수집한 뒤 3~8개를 Context에 넣되, 실제 수치는 골든셋 실험으로 결정한다.

## 8. D18 — Parent Document와 자기 검증

작은 Chunk는 검색 정밀도가 높지만 설명이 끊길 수 있다. Parent Document 방식은 작은 자식 Chunk로 검색한 뒤 의미가 완결된 부모 구간을 답변에 제공한다.

```text
원문 문서
  └─ 부모: 4장 고장 조치 절차
       ├─ 자식: 4.1 과열
       ├─ 자식: 4.2 진동
       └─ 자식: 4.3 유압 저하

자식 Chunk 검색 → 부모 구간 복원 → 중복 제거 → Context 구성
```

답변 생성 전후에 다음을 검사한다.

1. 핵심 주장마다 근거가 있는가?
2. 인용 문서에 실제로 해당 내용이 있는가?
3. 상충하는 개정본이나 예외 조건이 있는가?
4. 근거가 부족하면 재검색할 것인가, 답변을 보류할 것인가?

```text
검색 → 근거 충분성 판단
          ├─ 충분: 답변 생성 → 인용 검증 → 반환
          └─ 부족: 질의 재작성 → 재검색
                         ├─ 충분: 답변 생성
                         └─ 부족: 근거 부족 응답
```

재검색 횟수에는 상한을 둔다. 무한 반복보다 명시적인 실패 응답이 안전하다.

## 9. D19 — 종합 평가와 최적화

| 평가 축 | 확인 질문 | 측정 예시 |
|---|---|---|
| 검색 재현율 | 필요한 근거를 찾았는가? | Recall@k, Hit@k |
| 검색 순위 | 정답 근거가 상위에 있는가? | MRR, nDCG |
| 정답성 | 기대 답변의 핵심을 충족하는가? | 항목별 채점, 전문가 검토 |
| 근거성 | 답변 주장이 Context로 뒷받침되는가? | 주장 단위 판정 |
| 인용 정확성 | 표시한 출처가 실제 근거인가? | 인용 일치율 |
| 답변 보류 | 문서에 없는 질문을 거절하는가? | 거절 정밀도·재현율 |
| 성능 | 대기시간이 허용 가능한가? | P50·P95 지연시간 |
| 비용 | 품질 대비 비용이 적절한가? | 질문당 토큰·금액 |

### 실험 원칙

- 한 실험에서는 핵심 변수 하나만 변경한다.
- 같은 골든셋과 평가 코드를 사용한다.
- 평균뿐 아니라 질문 유형별 결과를 비교한다.
- 개선된 질문과 악화된 질문을 모두 기록한다.
- 품질 상승이 지연시간과 비용 증가를 정당화하는지 확인한다.
- 안전 절차와 수치는 현업 전문가가 표본 검토한다.

## 11. 최적화 우선순위

1. 원문과 메타데이터의 정확성을 확인한다.
2. 골든셋과 기준선을 만든다.
3. Chunk 경계와 문서 구조 보존을 점검한다.
4. `top_k`와 메타데이터 필터를 조정한다.
5. 약어·동의어 정규화를 적용한다.
6. 하이브리드 검색과 리랭킹을 비교한다.
7. Parent Document로 문맥 완결성을 높인다.
8. 답변 프롬프트와 보류 정책을 조정한다.
9. 품질, 지연시간, 비용을 종합해 설정을 확정한다.

## 12. 제조 RAG 안전 체크리스트

### 데이터·검색

- [ ] 문서의 개정 번호와 시행일이 보존된다.
- [ ] 폐기 문서가 기본 검색에서 제외된다.
- [ ] 표, 경고문, 단위, 절차 순서가 분할 과정에서 손상되지 않는다.
- [ ] 사업장·설비·제품·권한 필터가 서버 측에서 적용된다.
- [ ] 오류 코드와 부품 번호는 정확 일치 검색을 병행한다.
- [ ] 문서에 없는 질문이 골든셋에 포함된다.

### 답변·운영

- [ ] 핵심 주장에 실제 출처가 연결된다.
- [ ] 경고와 선행 조건을 생략하지 않는다.
- [ ] 상충 문서가 있으면 임의로 하나를 선택하지 않는다.
- [ ] 근거 부족 시 추측 대신 확인 필요를 알린다.
- [ ] AI 답변이 실제 설비 제어 명령과 분리된다.
- [ ] 질문, 검색 결과, 응답, 지연시간을 추적할 수 있다.
- [ ] 민감 정보는 로그에서 마스킹된다.
- [ ] 모델·임베딩·색인 변경 후 회귀 평가를 실행한다.

- [ ] 재현 가능한 설정 파일과 평가 리포트를 제출했다.

## 15. 핵심 정리

```text
좋은 RAG = 좋은 데이터
         + 측정 가능한 검색
         + 완결된 Context
         + 근거를 지키는 생성
         + 반복 가능한 평가
```

RAG 최적화의 출발점은 모델 변경이 아니라 평가 가능한 골든셋이다. 검색과 생성을 분리해 측정하고, 제조 현장의 문서 버전·권한·안전 조건을 품질 지표와 함께 관리해야 한다.
